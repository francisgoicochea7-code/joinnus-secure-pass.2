Errores que me salieron en SonarQube

Joinnus Secure Pass — versión 2

Análisis estático · SonarQube Community 26.10 · 3 de noviembre de 2026

1. De qué va este informe

Cuando pasé SonarQube por el proyecto me salieron 20 incidencias. Al principio pensé que eran 20 problemas distintos, pero al mirarlas con calma me di cuenta de que en realidad son cuatro reglas repetidas en varios archivos. Este documento tiene dos partes: el listado completo y una explicación de por qué aparece cada error, con ejemplos del código.

No voy a entrar todavía en cómo los corregí. La idea es entender primero el diagnóstico: qué vio SonarQube, en qué archivo lo vio y por qué esa regla existe. Las correcciones las dejo para otro documento, porque mezclar las dos cosas hace que se pierda el hilo.

2. Cómo hice el análisis

Usé SonarQube Community 26.10 en local, con el proyecto joinnus-secure-pass, versión 2.0.0. El análisis se hizo sobre el código de la aplicación y no sobre las pruebas. No mandé cobertura porque la suite que tengo es un script propio y no está instrumentada; preferí no inventar un porcentaje que no existe.

5. Por qué aparece cada error

5.1 Promesas sin manejar (S9383) — 7 incidencias

Esta es la regla que más veces salió. En JavaScript, cuando llamas a una función async o usas .then(), lo que devuelve es una promesa. Si esa promesa falla y nadie la espera con await, no le pone un .catch() o no la marca con void, el error se queda sin manejar. El programa no necesariamente se cae, pero tampoco te enteras de lo que pasó.

En el backend salió en el arranque. El código era más o menos así:

esperarBase().then(() => {
  app.listen(CFG.port, '0.0.0.0', () => {
    console.log('API lista');
  });
});

Ahí no hay .catch(). Si la base de datos no responde, la promesa se rechaza y el error no se explica en ningún lado. SonarQube lo marca porque el arranque puede quedarse a medias sin que el usuario sepa por qué.

En el frontend pasó algo parecido con la API:

SecurePassAPI.usarApi().then(aplicar);

Si usarApi() falla, aplicar no se ejecuta y no hay un camino para mostrar el error. En staff.js había cuatro casos de funciones async llamadas sin await ni .catch(), por ejemplo:

ui.formVerificar.addEventListener('submit', e => {
  e.preventDefault();
  verificar(ui.qrTexto.value, false);
});

verificar es asíncrona. Si falla la petición, la promesa queda flotando. No es que el formulario esté mal escrito; el problema es que no hay un manejo claro del error.

En resumen: son 7 casos de lo mismo. La regla no dice que la aplicación esté rota, sino que hay errores que pueden pasar desapercibidos.

5.2 Campo sin etiqueta (InputWithoutLabelCheck) — 1 incidencia

En frontend/historial.html está el selector que sirve para filtrar por código de entrada:

<select class="input" id="filtro-codigo" style="...">
  <option value="">Todas las entradas</option>
</select>

El selector funciona bien, pero no tiene un <label for="filtro-codigo"> ni un aria-label. SonarQube lo marca porque un lector de pantalla no sabe qué es ese campo. Tampoco puedes hacer clic en el texto de la etiqueta para enfocarlo, porque no hay etiqueta. Es un problema de accesibilidad, no de que el filtro deje de funcionar.

La regla revisa los campos de formulario y avisa cuando no encuentra una etiqueta válida. En este caso el campo es un select, pero la lógica es la misma para un input.

5.3 Math.random en contexto de seguridad (S2245) — 2 incidencias

Math.random() no es un generador seguro. No es criptográfico y se puede predecir, así que no debería usarse para tokens, códigos o cualquier cosa que alguien pudiera adivinar. En frontend/js/api.js aparecía en dos sitios: como respaldo para generar la semilla de un código y para armar el id de un registro del historial.

semilla = Math.floor(Math.random() * 0xffffffff).toString(16).toUpperCase();

id: 'H' + Date.now().toString(36).toUpperCase() + Math.floor(Math.random() * 900 + 100),

En una demo no parece grave, pero SonarQube no sabe si es demo o producción: ve un generador predecible en una parte donde se están creando códigos y lo marca como vulnerabilidad. Si eso se usara para un token de verdad, alguien podría adivinar valores. Por eso la regla se llama Pseudorandom number generators should not be used in security contexts.

Ojo: el problema no es usar Math.random() para cualquier cosa. Para un sorteo o un detalle visual no importa. Importa cuando el valor tiene que ser impredecible.

5.4 Métodos numéricos globales (S7773) — 10 incidencias

SonarQube prefiere Number.isNaN, Number.parseInt, Number.parseFloat y Number.NaN en lugar de las versiones globales. No es que el programa esté mal, pero las globales hacen conversiones que a veces sorprenden.

En app.js había cinco casos como este, para formatear fechas:

if (isNaN(d)) return '—';

En api.js había uno para validar el precio:

if (isNaN(numero) || numero < 0) {
  return { ok: false, mensaje: 'El precio debe ser un número válido en soles.' };
}

Y en backend/index.js había cuatro: dos en los parsers de PostgreSQL (parseInt y parseFloat), uno en isNaN(precio) y otro en el uso de NaN.

¿Por qué la regla prefiere Number.*? Porque isNaN('') devuelve false, aunque '' no sea un número, y isNaN('abc') devuelve true. Number.isNaN solo devuelve true si el valor es realmente NaN. Con parseInt pasa algo parecido: sin base explícita puede interpretar números con ceros a la izquierda de forma rara. Y Number.NaN deja más claro que se está usando el NaN numérico y no una variable global.

En resumen: son 10 detalles de estilo y precisión, no 10 fallos que se vean a simple vista. Aun así, SonarQube los marca porque ayudan a que el código sea más predecible.

6. Lo que este informe no dice

No quiero que se entienda más de lo que es. Este documento no dice que la aplicación esté rota ni que estos sean los únicos problemas posibles. Son las incidencias que detectó SonarQube con las reglas que tenía activas en ese momento.

SonarQube es un análisis estático: lee el código, pero no ejecuta la aplicación. Por eso no reemplaza un escaneo dinámico como OWASP ZAP, que prueba la aplicación en funcionamiento y puede encontrar otras cosas. Tampoco estoy diciendo que los 20 errores sean todos graves: algunos son de accesibilidad o de estilo, no de seguridad.

Alcance: el análisis se hizo en local, sobre la versión 2 del proyecto, y se evaluó el código nuevo. La cobertura no se midió porque la suite no está instrumentada. Las correcciones no forman parte de este documento.

7. Cierre

Al final, el análisis inicial me dejó 20 incidencias, pero al agruparlas se entiende mejor: 8 bugs (7 promesas y 1 etiqueta), 2 vulnerabilidades (Math.random) y 10 code smells (métodos numéricos). La mayoría son detalles de cómo está escrito el código, no fallos que se vean a simple vista.

Lo que más me sirvió fue separar el listado de la explicación. Ver los 20 juntos impresiona; entender que son cuatro patrones repetidos hace que el análisis sea mucho más manejable. Las correcciones las documento aparte, cuando toque.
